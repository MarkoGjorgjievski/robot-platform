## 2. The problem v1.1b must solve (user's framing)

> "If user sees 16 good fields with example values, they expect 16 fields to be extracted. We shouldn't provide 4. They don't care how we look for it."

This is correct product framing. The dogfood evidence:

- Analyze step shows 16 fields with correct example values: `price: $62.17`, `weight: 12.3 Ounce`, `diet_type: Kosher`, `size_options: [30 Pieces, 15 Pieces]`, etc. The AI clearly **sees** these values during analyze (screenshot + DOM markdown + structured data input).
- Extract step resolves only 4/16. The AI XPath generator gets the field name but NOT the example value, so it has to invent selectors from scratch. It guesses; usually wrong on Amazon-class pages.
- The "Cached — 1 runs, 0% reliability" badge presented on Run 2 is technically honest (last run failed the 30%-confidence success threshold) but the dashboard still rendered the unreliable cache as if it were authoritative schema. UX bullshit.

### The three threads of v1.1b

**A. Extraction quality — example-as-XPath-target (highest leverage)**
- Currently `agent.generateSelectors(capture, missingFields, pageType)` receives only field names (`weight`) and field types (`string`).
- Add: pass each field's `example_value` from the analyze step into the XPath prompt as a *target* to find.
- This is reverse-search rather than forward-generation. Much higher hit rate.
- Persist example values in the cache too, so they survive cache hits and feed the rediscovery loop.
- Expected ceiling: 25% → 75-88% on Amazon-class pages. Not 100% — that needs v2.1 click-to-select.

**B. Cache reliability gating in the UI (highest signal on UX honesty)**
- When `successRate < 30%` OR `consecutiveFailures > 0`, don't present cache as authoritative schema.
- Either auto-run analyze with `force=true`, or show explicit "Cache is unreliable — re-run AI" affordance.
- Today's behavior: cache hit fires whenever `consecutiveFailures < 5`, even if `successful_runs = 0`. Wrong.

**C. Visual distinction for empty-path entries (highest "stop confusing the user" payoff)**
- Today's schema editor renders empty-path fields identically to reliable cached fields (same checkbox, `—` in Example column).
- v1.1a's analyze response already returns `needsRediscovery: true` on these — UI ignores it.
- Direction: group empty-path fields under "AI proposed last time, will retry on extract" subsection, or grey them out, or pin them at the bottom with a "pending discovery" hint.

## 4. Where v1.1a's verification stopped

Tasks 4 (`__NEXT_DATA__` to AI) and 5 (entity-subtree identification) were not exercised because Amazon doesn't use Next.js. **Before shipping v1.1b, test these on a real Next.js / Nuxt e-commerce site** (e.g., a Shopify store with hydration, or a Vercel-hosted store). If they fail there, fold the fixes into v1.1b. Don't ship v1.1b on top of unverified v1.1a.

Task 6 (shape validator) showed a suspicious confidence drop between Run 1 (25%) and Run 2 (13%). Could be LLM nondeterminism, could be the validator over-rejecting. Investigate before v1.1b lands — look at `packages/scraper/src/shape-validator.ts` rejection patterns and check whether common Amazon values (long descriptions, dimension strings) are getting bounced.
