# v1.1b Implementation Plan — Extraction Quality + Always-Consult Cache + Honest UI

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Lift extraction resolution on hard pages by giving the XPath generator the value to target (reverse-search), make the pipeline always consult the domain cache, and make the dashboard show current-page truth instead of stale cache snapshots.

**Architecture:** Three independent, sequential phases gated by a Phase 0 verification of v1.1a. Phase 1 makes `agent.generateSelectors` multimodal (screenshot + DOM) and have it return the value it sees alongside each XPath. Phase 2 deletes three `consecutiveFailures < 5` gates in `scraper.ts` (the cache model is already correct in `domain-cache.ts`). Phase 3 makes analyze capture + resolve on cache-hit and removes a misleading reliability badge.

**Tech Stack:** TypeScript, Vitest, tRPC v11, Drizzle ORM, Playwright, Anthropic SDK; packages `@robot/agent`, `@robot/scraper`, `@robot/api`, `@robot/dashboard`.

**Spec:** `docs/superpowers/specs/2026-05-20-v1.1b-design.md` — read the "Cache model" + "Code reality" sections before Phase 2.

**Commit convention:** The user commits manually. Each task ends with a *suggested* commit message — do NOT run `git commit` unless the user explicitly asks. Stage nothing automatically.

### Task 0.3: Rework `findEntitySubtree` for nested / SKU-keyed structures

Phase 0.1 found that `findEntitySubtree` returns root `$` score 0 on Nike's `__NEXT_DATA__` because `scoreObject` exact-matches only an object's own direct keys, and Nike's entity fields use descriptive key names (`colorDescription`, `availabilityDate`, `productInfo`, `prices`) that don't exact-match `SCHEMA_KEYS`. Result: the full 100 KB blob is sent to the AI instead of a scoped subtree. Fix the heuristic so it locates a single product entity node, without breaking the five existing tests and without scoping so wide it doesn't reduce noise (`pageProps` is 99.7 % of the blob — selecting it is a non-fix) or so wrong it drops the page's product.

Real fixture data has been captured to `/tmp/nike-nextdata.json` (100 KB). Confirmed facts about it:
- The page's product is at `props.pageProps.selectedProduct` (a full product object, ~11.7 KB) and is duplicated under `props.pageProps.productGroups[N].products["<SKU>"]`.
- The product object's direct keys include `colorDescription`, `brands`, `availabilityDate`, `colorCode`, `globalProductId`, `merchProductId`, `productInfo`, `prices`, etc. — field-rich.
- `selectedProduct.productInfo.title` === `"Air Jordan 12 Retro"`; `selectedProduct.prices.currentPrice` is a positive number.
- `props.pageProps` serialized ≈ 100 KB (≈ the whole blob); a single product node ≈ 11.7 KB.

### Task 0.4: Prioritize structured-data (`inline://`) sources over size in `collectAiAnalysisSources`

Re-running the live Nike diagnostic after Task 0.3 revealed a coupled bug. `collectAiAnalysisSources` (`packages/api/src/routers/lib/collect-ai-analysis-sources.ts`) ranks all candidate AI sources by `bodySize` descending and `slice(0, MAX_SOURCES=5)`. Before Task 0.3, the 100 KB unscoped `nextData` always won that race. Now that Task 0.3 correctly scopes it to ~4.6 KB, the high-signal `inline://nextdata` source LOSES the size race to large junk intercepted requests (privacy-compliance frames, Salesforce chat config, i18n blobs) and gets dropped from the top 5 — so the best source never reaches the AI. Fix: structured-data (`inline://`) sources are always retained; the size cap applies only after they're kept.

```typescript
export function cachedFieldsFromCache(
  fieldPaths: Record<string, FieldPathSet>,
  liveValues?: Record<string, unknown>,
): CachedFieldSummary[] {
  return Object.entries(fieldPaths).map(([name, pathSet]) => {
    const bestPath = [...pathSet.paths].sort((a, b) => {
      const aRate = a.hits + a.misses > 0 ? a.hits / (a.hits + a.misses) : a.confidence;
      const bRate = b.hits + b.misses > 0 ? b.hits / (b.hits + b.misses) : b.confidence;
      return bRate - aRate;
    })[0];
    const totalHits = bestPath?.hits ?? 0;
    const totalMisses = bestPath?.misses ?? 0;
    const hitRate = Math.round(totalHits / Math.max(1, totalHits + totalMisses) * 100);
    const liveValue = liveValues?.[name];
    const example = liveValue !== undefined && liveValue !== null
      ? String(liveValue).slice(0, 200)
      : (bestPath?.lastValue != null ? String(bestPath.lastValue).slice(0, 200) : undefined);
    return {
      name,
      type: inferFieldType(name),
      description: pathSet.paths.length === 0
        ? 'Cached field (discovered previously, awaiting re-discovery)'
        : `Cached field (${bestPath?.source ?? 'unknown'} source, ${hitRate}% hit rate)`,
      required: true,
      example_value: example,
      tier: undefined,
      needsRediscovery: pathSet.paths.length === 0,
    };
  });
}
```

```markdown
### 💡 Cache lifecycle — pruning, within-batch correction, backfill (deferred from v1.1b)

The v1.1b cache work intentionally stopped at "always consult the cache." The existing per-path prune (≥5 uses & ≤10% hit) and 5-path cap are kept as-is. Deferred, to be designed against real volume data:
- **Per-path prune tuning** — revisit the 5-use / 10% / 5-path-cap constants once we have multi-thousand-run domains.
- **Within-batch second pass** — when a path discovered late in a batch would have fixed earlier inputs in the same batch, re-run the batch's own failed fields at the end.
- **Historical backfill** — re-scrape already-delivered data when a materially better path appears (opt-in; expensive).
- **Exploration-rate control** — today cross-validation exercises all paths every run; if early-exit is ever added for cost, exploration must be reintroduced as a rate so challenger paths still earn hits.

Why milestones were rejected: absolute total-use milestones (1/5/.../10k) can't judge a path at small N and don't scale across customers (100-input vs 100k/day). Per-path evidence is the right primitive — which the existing prune already uses.
```
