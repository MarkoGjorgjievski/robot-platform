## Problem

Dogfooding v1.1a on an Amazon Godiva product surfaced the gap that defines v1.1b:

> "If the user sees 16 good fields with example values, they expect 16 fields to be extracted. We shouldn't deliver 4. They don't care how we look for it."

The AI **sees** all 16 values during analyze (via screenshot + DOM markdown + structured data) and quotes correct examples. Extract then resolves only 4/16, because XPath generation gets the field *name* but not the *value*, so it invents selectors blind and usually misses on Amazon-class pages. Compounding this, the dashboard presented an unreliable cache row ("1 run, 0% reliability") as if it were authoritative schema.

v1.1b closes three things: extraction quality (give the XPath generator the value to target), a correct cache model (accumulator, not snapshot), and honest per-run UI.

---

## Cache model (the conceptual core — read this first)

This model corrects the handoff's "cache reliability gating" framing, which was wrong.

1. **The cache is an accumulator, never a snapshot.** Paths are *added* across runs. A single failure never clears anything. The cache as a whole is never "unreliable" — it is a growing set of paths, some of which are correct for some product/layout variants on the domain.

2. **Page structure varies product-to-product**, even within the same domain / country / category. So **multiple paths per field coexist** — `weight` may carry several XPaths, each correct for a different layout variant. The pipeline tries them; whichever fits the current URL wins.

3. **The pipeline is always the same:** try cached paths per field → AI fills in for fields that didn't resolve → new AI paths get appended. There is **no** reliability gate, **no** "force re-run analyze," **no** consecutive-failures reset.

4. **Learning is retroactive for ranking, not for delivered data.** When a better path is discovered, future runs benefit automatically because ranking promotes it. Already-delivered extractions are *not* re-scraped — that is a backfill feature, out of scope here.

5. **Most of this model is already implemented** in `packages/scraper/src/domain-cache.ts` — see "Code reality" below. v1.1b's cache work is therefore small: remove the gates that make the pipeline *ignore* the cache, and otherwise leave the existing (already-sensible) behavior alone.

### Code reality (verified 2026-05-20)

The destructive "milestone ladder" / "consecutive-failures reset" that the handoff worried about **was never in the code.** What actually exists:

- **No auto-reset.** `saveDomainCache` explicitly *"flags degradation but NEVER auto-resets — human review required"* (`domain-cache.ts:391`). The `consecutiveFailures >= 5` check there only logs a warning; cache data is never wiped.
- **Multi-path coexistence.** Up to 5 paths per field (`mergeFieldPaths`, cap at `:492-500`).
- **Recency-weighted ranking.** `pathScore()` (`:569`) discounts stale misses; `resolveFromCache` sorts by it with human-paths-first.
- **Cross-validation.** `resolveFromCache` tries *all* of a field's paths and takes majority agreement (`:144-149`) — effectively always-on exploration.
- **Per-path pruning, the good kind.** A path is dropped only after **≥5 of its own uses at ≤10 % hit rate** (`:485-490`). This is the per-path-evidence primitive — *not* the absolute milestone ladder. Plus the max-5-paths cap.

**Why the milestone ladder would have been wrong (kept for the record):** absolute total-use milestones can't judge a path at small N (hit-or-miss, no signal), and don't scale across customers (a 100-input customer never reaches the 1k/10k rungs; a 100k/day customer exhausts them by lunch). The right primitive is per-path evidence — which the existing prune already uses.

**The one genuine bug** is in `scraper.ts`, not `domain-cache.ts`: the `consecutiveFailures < 5` **gates** at `:59` (analyze), `:279` and `:324` (extract) make the pipeline *stop consulting* the cache after 5 failures. Deleting those gates is the actual accumulator fix.

**Deferred to a future cache-lifecycle spec:** per-path-evidence pruning tuning, within-batch second-pass, historical backfill, and explicit exploration-rate control. None are needed for v1.1b because cross-validation already exercises all paths and the existing prune is already conservative.

## Phases

Each phase is independently shippable and verifiable. Phase 0 gates the rest.

### Phase 0 — Verify the v1.1a foundation

v1.1a's structured-data work (Tasks 4–5: `__NEXT_DATA__` → AI, entity-subtree scoping) was never exercised — Amazon has no Next.js. The shape validator showed a suspicious confidence drop (Run 1 25 % → Run 2 13 %) that could be over-rejection.

- **Next.js/Nuxt dogfood.** Run a real Next.js or Nuxt e-commerce product page through analyze + extract. Confirm `collectAiAnalysisSources` emits `inline://nextdata...` sources and that `findEntitySubtree` scopes the blob. Capture the resolution rate.
- **Shape-validator audit.** Inspect rejection logs against the existing `www.amazon.com / detail` cache row. Verify long product descriptions and dimension strings (`"12.3 x 8.1 x 2.4 inches"`) are **not** bounced by `UI_LABEL_PATTERNS` or `DESCRIPTION_MIN_LENGTH`. Tighten patterns / lengths only where a real false-reject is found.
- **Gate:** fix anything that blocks before starting Phase 1. If Tasks 4–5 are fundamentally broken on Next.js, fold the fix in here.

**Done when:** a Next.js page extracts with `inline://nextdata` sources attributed, and the shape validator's rejection set on the Amazon row contains no legitimate values.

**Findings (verified 2026-05-20 against `nike.com` Air Jordan 12 product page):**
- **Task 4 ✅** — `__NEXT_DATA__` (100 KB) and one JSON-LD blob were captured and both reached the AI as `inline://nextdata` + `inline://ld+json[0]`. `agent.extractFromApi` on the `nextData` source returned `product_name="Air Jordan 12 Retro"`, `price=200`, `color="Black/Varsity Red"` with high confidence and real dot-paths (`props.pageProps.productGroups[3].products.CT8013-003.productInfo.title`).
- **Task 5 ⚠️ → fixed in Task 0.3** — `findEntitySubtree(nextData)` returned root `$` with score 0. Nike splits entity fields across child sub-objects (`productInfo.title`, `prices.currentPrice`) keyed by SKU, so no single node has ≥2 of the scorer's direct schema keys. The code falls back to the full blob, so extraction still worked, but the noise-reduction the source was meant to provide didn't fire. The user chose to fold a proper fix into v1.1b — see Task 0.3.
- **0.2 ✅** — shape validator does not over-reject (audit test `shape-validator-audit.test.ts`, committed `ab381a1`).

### Task 0.3 — Rework `findEntitySubtree` for nested / SKU-keyed structures

The current `scoreObject` counts only an object's *own* direct keys against `SCHEMA_KEYS` with exact match. Real SSR blobs (Nike) split a product's fields across child sub-objects and key product maps by SKU, so the entity node scores 0. Rework the heuristic so it locates the node that *aggregates* an entity's fields, while still preferring the most concentrated node and not over-selecting big container nodes (e.g. `pageProps`, whose own keys like `productGroups`/`colorwayImages` superficially contain schema tokens). Must keep all five existing `entity-subtree.test.ts` cases passing, and must scope the Nike fixture to a node that contains the product title + price and is substantially smaller than the full blob.

### Phase 1 — Thread A: example-as-XPath-target (unified multimodal call)

The highest-leverage change. Reverses XPath generation from *forward invention* ("write a selector for `weight`") to *reverse search* ("here's the page, find the value and give me a selector that returns it").

- **`agent.generateSelectors` becomes multimodal.** It already receives the full `PageCapture` (screenshot included) but today only sends truncated HTML. Change it to send the **screenshot + DOM + structured-data summary** alongside the field list — the same multimodal lens the analyze step uses.
- **One call does discovery + targeting.** For each unresolved field, the AI both identifies the value visible on the page and returns an XPath that selects it. The tool's return shape gains a `value` per field: `{ name, xpath, value, confidence }`.
- **No dependency on a prior analyze pass.** Because the call reads the page directly, it behaves identically on cache-miss and cache-hit. This is why we chose the unified call over a two-step "analyze produces examples, generator consumes them" design — the two-step version needs a second AI pass on cache-hit to get current-URL examples.
- **Wiring in `extract` (`scraper.ts:357-409`, the XPath fallback step):** the AI-returned `value` flows through `tryAssign` → `validateFieldShape`; the `xpath` is what gets persisted to the cache via `saveDomainCache`. The retry path (`retrySelectorGeneration`) gets the same multimodal treatment for consistency.
- **Ollama fallback:** Ollama may not be multimodal in all local setups. Keep the text-only prompt for the Ollama branch (degraded but functional); the multimodal upgrade applies to the Anthropic branch. Document this asymmetry.

**Expected lift:** 25 % → 75 %+ resolution on Amazon-class pages. Not 100 % — that needs v2.1 click-to-select.

**Done when:** re-running the Amazon Godiva case resolves substantially more than 4/16 fields, with the newly-resolved fields attributed to `xpath` source and their selectors persisted to the cache.

### Phase 2 — Always consult the cache (delete the gates)

Per "Code reality" above, the accumulator model is already implemented. The only change is removing the gates that make the pipeline ignore the cache. **No path-ranking, early-exit, or exploration code is added** — those either already exist (ranking, cross-validation) or aren't worth it (early-exit would weaken cross-validation for negligible savings, since path execution is already cheap and the real perf win — skip AI when cache resolves — already happens).

- **Delete the three `consecutiveFailures < 5` gates** at `scraper.ts:59` (analyze), `:279`, and `:324` (extract). The cache is always consulted; per-URL resolution decides what works. Keep the warning log in `saveDomainCache` (it's harmless and useful for human review).
- **Keep the existing per-path prune (`:485-490`) and max-5-paths cap (`:492-500`) untouched.** They already implement the per-path-evidence principle.
- **Leave ranking, recency weighting, cross-validation, and no-auto-reset as-is** — already correct.

**Done when:** the existing Amazon row (`total_runs=2, successful_runs=0, consecutive_failures=2`) is consulted on the next run instead of skipped, proven by a test that calls the resolution path with a high-consecutive-failures cache and confirms cached paths are still attempted.

### Phase 3 — Thread C: honest per-run UI

- **analyze cache-hit shows live examples.** Today analyze cache-hit (`scraper.ts:59-99`) returns `example_value` from `bestPath.lastValue` — the value from whatever URL was extracted *last*, without ever looking at the current page. Change it to **capture the current URL and resolve cached paths**, so the Example column reflects the current page. (analyze gains a Playwright capture on cache-hit; no AI call needed for resolved-path fields.)
  - **Capture reuse — explicit non-goal for now.** extract still recaptures even after analyze captured, because captures are point-in-time and a user may extract minutes later. The double-capture only occurs within a single analyze-then-extract session — acceptable. Capture-reuse (passing the capture via `captureId`) is a later optimization, noted but out of scope.
- **Kill the misleading badge.** Remove the "Cached — N runs, 0 % reliability" authoritative-schema badge. Replace it with per-run resolution truth: the results table already returns one row per toggled field (value / status / source / confidence) from v1.1a. Reliability is a property of *this run's output*, not a cache-level verdict.
- **No "pending discovery" field category.** A field either resolved on this run or it didn't (`—` / `not_found`). Empty-path fields are not categorically different from "fields whose paths didn't resolve on this URL" — both just mean "AI tries next." Do not build a separate UI bucket for them.

**Done when:** pasting a URL that hits the Amazon cache shows current-page example values (not stale ones), no "0 % reliability authoritative" badge appears, and the results view communicates per-field resolution for the run.

## Out of scope (deferred)

- **Cache lifecycle (its own spec):** tuning the existing per-path prune + 5-path cap; exploration-rate control; **within-batch second pass** (re-run a batch's own failed fields using paths learned later in the same batch); **historical backfill** (re-scrape already-delivered data when a better path appears). All deferred and to be designed against real volume data.
- **Capture reuse** between analyze and extract (Phase 3 note).
- **Cross-source corroboration** weighting structured-data sources above XPath inferences (v1.1a leftover).
- **Click-to-select (v2.1)** — the human-supplied target. Phase 1's AI-supplied target is the reverse-search precursor.
- **Cache hit eclipsing user-typed requested fields** (`docs/ideas.md`) — separate dashboard-UX pass.

## Success criteria (whole release)

- Amazon Godiva resolution climbs from 4/16 toward the analyze-time field count (target ≥75 %).
- A Next.js page extracts with `inline://nextdata` sources attributed.
- The cache is consulted on every run (no consecutive-failures gate); paths accumulate and ranking improves over runs.
- No stale cross-URL example values and no "0 % reliability authoritative" badge in the UI.
- `pnpm -r test` and `pnpm -r typecheck` green across the workspace.
